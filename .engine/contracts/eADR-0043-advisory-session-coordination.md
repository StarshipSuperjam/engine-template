title: Cross-session worker coordination is advisory; the payload is durable and the doorbell is live

## Decision

Active Engine worker sessions may coordinate while work is in flight — breaking-change warnings, overlap
warnings, prerequisite handoffs, bounded status, integration and revalidation notices — under one governing
law: **live communication may reduce latency and rework, but Engine correctness, authority, consent, and
future-session truth never depend on a message being delivered.** Git, GitHub, the Engine's receipts and
contracts, the settled specification, and the serialized-integration machinery (eADR-0042) remain the sole
authorities. This capability makes that lifecycle cheaper and less conflict-prone when a runtime supports
live messaging; it never replaces a correctness property of it.

Seven properties bind every part of this capability:

1. **Payload durable, doorbell live.** The durable carrier for a coordination signal is a typed,
   digest-verified, machine-marked **notice** kept in one Engine-maintained comment on the GitHub work item
   it concerns. It is a **best-effort durable cache of advisory signals, not a tamper-evident system of
   record**: GitHub stamps actor and time on the latest edit, but a maintained comment is multi-writer with
   no compare-and-swap, so a peer can lose, evict, or overwrite an entry, and a write-collaborator can alter
   or delete one. That is acceptable precisely because the layer is advisory — canonical state always wins.
   The live lanes (a runtime's own cross-session messaging) carry only a fixed-format one-line **poke**
   pointing at the durable notice. A held, refused, dropped, forged, suppressed, or stale message can never
   become truth.

2. **No free-prose slot.** Every rendered line — the notice's operator-facing line and the live poke — is
   fixed copy generated by tool code from closed enums. A peer session's model never authors text that
   another session's model then reads as content. Repo-native identifier fields a receiver must read
   (branch names, changed paths) are still attacker-influenceable strings, so they are charset- and
   length-constrained, rendered fenced and never as instructions, and kept out of the boot and
   operator-facing lines (which carry only enum kinds and integer counts). This is the decisive
   prompt-injection mitigation and it narrows the identifier surface; neither is claimed closed — both
   residuals are named in Anti-choice.

3. **Advisory-only, never a proxy.** A notice may report that an authoritative fact exists ("PR #N merged");
   it may never *be* that fact. It can never satisfy or stand in for operator approval, a permission prompt,
   `guardrail-ack`, a review or QA attestation, merge eligibility, exact integration-candidate freshness
   (eADR-0021 / StarshipSuperjam/engine-template#915), canon or specification authority, credentials, or deployment authority. The receiver
   verifies the authoritative surface. This is enforced mechanically in **two layers**: a **runtime
   comment-only transport guard** (`coordination_board.comment_only`) wraps every transport coordination
   holds so it can issue only reads and the two comment-write shapes, raising on anything else — the
   mechanical guarantee, which holds even against an indirected or future-added write; and a **fail-closed
   static check** (a hard CI gate) that additionally trips on a merge/label/status/body call or an
   authority-writer import written directly in a coordination file. The runtime guard is the guarantee; the
   static scan is the early tripwire on top of it (it does not follow the import graph, and does not claim
   to).

4. **Bounded emission, no broadcast; each signal rides its own determined trigger.** Notices are emitted only
   at semantically meaningful points, never per file edit and never on a timer. A signal that rides a
   session's *deliberate action* (declaring, claiming, abandoning, submitting, or preparing work) fires from
   that action. A signal that is a *reaction to a merge* — the base advanced (revalidation), a merge touched a
   peer's declared surface (dependency-update), the integration slot freed (next-in-queue) — fires from the
   merge EVENT itself, a `pull_request: closed` workflow gated on merge, never from a human remembering to run
   a verb: the base advances the instant the merge lands, so the emission must be as deterministic as the
   event. Emission is deduplicated on the structured condition; a live poke fires only on a durable-board
   change; emission is single-attempt and fire-and-forget, and can never block, fail, or alter the behaviour
   of the step or event it rides.

5. **Repo-native identifiers only on durable surfaces.** A durable notice carries only
   repository-native facts — pull request and issue numbers, branch names, commit SHAs, tool and event
   names, timestamps. Worktree paths, machine names, and session identifiers never reach GitHub; they live
   only in the ephemeral live lane and the gitignored local ledger.

6. **Ephemeral bookkeeping, never a corpus.** Read/unread cursors and bounded measurement metadata live in a
   gitignored local ledger, fingerprinting the structured condition and failing toward showing more. Full
   peer exchanges never become a second permanent knowledge store; a future session reconstructs project and
   Engine truth without any coordination-message history.

7. **A sanctioned message lane, not a relaxed non-interference norm.** Peer non-interference over the
   *filesystem* stays absolute — a session never sweeps or edits a peer's worktree. This decision opens a
   *message* lane only: typed, advisory, bounded, and carrying no authority over the receiver.

## Significance

This is the coordination layer that sits on the concurrency law (eADR-0042) and the intra-Build worker DAG
(eADR-0041) without weakening either. Later work must keep coordination advisory: any future notice kind,
emitter, or provider adapter inherits all seven properties, and no adapter may widen what a message can cause
beyond "prompt a peer to re-check canonical state." The provider-neutral shape means a runtime with no live
messaging remains fully first-class through the durable lane alone.

## Rationale

Concurrent sessions already make the repository multi-writer (eADR-0042); until they can signal each other
while active, the human operator is the routine message bus and overlapping or dependent work is discovered
only at reconciliation — safe but late. Coordination removes that lag. It must be advisory because delivery
is genuinely unreliable across runtimes and refusable by design, so any correctness resting on it would be
false consent of exactly the kind the freshness floor (eADR-0021) exists to refuse. The payload is durable on
GitHub because that surface already carries platform-stamped attribution and outlives every session; the
doorbell is live because latency is the only thing live delivery can safely add. This is a new decision
domain — eADR-0041 owns coordination *inside* one Build, eADR-0042 owns *integration* across builds; neither
governs *advisory messaging* across active sessions — so it is a new founding record rather than an overload
of either.

## Anti-choice

Rejected: a general chat channel or workflow engine between sessions. Rejected: a conversational
status-request/reply kind — status is answered by declarative notices plus the live roster, never a
back-and-forth. Rejected: per-file locking or any admission control by overlap — overlap warnings prompt a
human decision, they never gate. Rejected: a free-prose field in a notice or poke — behaviour-driving fields
are closed enums and rendering is fixed tool code, because notice text is ultimately read by a model.
Rejected: waking an idle peer to deliver advisory traffic. Starting a new turn on an idle thread (Codex
`turn/start`) creates an in-progress turn and spends the peer's budget for a signal that never needs
immediacy, so an **idle peer receives the durable notice only** — never a live poke that activates it.
`send_message_to_thread` is **not assumed passive** (its contract sends a background follow-up prompt that
may start inference) and stays unused until enqueue-only behaviour is documented or proven;
`thread/inject_items` is rejected because it persists into conversation history — unsuitable for an
ephemeral, auditable signal. The one permitted Codex live path is a **bounded `turn/steer` of an
already-active peer turn**: it targets an existing turn, never wakes an idle thread or creates one, though
it may affect token use. A capability slot is reserved for any future *verified* passive inbox API. All of
this is **sender-side discipline** — the Engine drives no peer runtime — whose failure is rendered harmless
by the receiver law below, never a mechanical guarantee. Rejected: a second session-identity registry —
routing identity is the pull request or issue, derived live from GitHub, because no durable session identity
exists and the ephemeral one is last-writer-wins under concurrency (eADR-0034).

Residuals are named, not claimed closed. (1) A receiving model still reads a poke as text, so a hostile
message is a prompt injection like any hostile input — bounded by fixed rendering, same-control-plane send
gating, and the standing receiver law that any message is untrusted until canonical state is re-verified.
(2) The repo-native identifier fields a receiver must read (branch, paths) are attacker-influenceable
strings — bounded by charset/length constraints, fenced rendering, and their exclusion from the
operator-facing lines, not closed. (3) Any collaborator with repository write can post a well-formed notice,
alter one, or delete one: the digest proves integrity and de-duplicates, it is **not** a signature and does
not screen a correct-digest forgery — the real bound is that notices carry no authority and the receiver
re-verifies canonical state, so no trusted-creator filter is needed. (4) The board is a multi-writer comment
with no compare-and-swap, so a concurrent write may lose a peer's entry, a write-collaborator may suppress
one, and a burst of forged entries may evict live ones under the cap — each bounded to lost *advisory
latency*, never lost correctness, since delivery was never load-bearing; the cap eviction never drops a
higher-priority live entry.
